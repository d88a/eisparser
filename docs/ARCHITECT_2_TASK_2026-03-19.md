## 2) Проблема

Текущий pipeline формально работает, но качество Stage 2/3 недостаточное:
1. в карточках появляются записи с пустым/непригодным `город`,
2. Stage 3 не умеет стабильно маппить районные/окружные/станичные названия к координатам,
3. часть закупок не получает валидную ссылку 2ГИС из-за слабой нормализации населенного пункта.

## 3) Что исправить (P0)

## P0.1. Гарантировать заполнение `city` в Stage 2

Сделать в `src/pipeline.py` и связанных сервисах:
1. Жесткий fallback для `city`, если AI вернул пусто/мусор:
   - брать из `address`,
   - при необходимости парсить из текста документа.
2. Ввести проверку пригодности значения `city`:
   - не пустое,
   - не служебный маркер (`-`, `не найдено`, и т.п.),
   - не слишком длинная/неструктурная строка.
3. Если `city` восстановлен fallback-ом:
   - явно логировать источник (`city_source=ai|address|doc_parse`).

Критерий приемки:
1. Для новых обработанных закупок `city` не пустой в UI.
2. В логах видно, откуда взят `city`.

## P0.2. Нормализация населенного пункта перед GIS lookup

Сделать в `src/services/gis_service.py` (или эквивалентном слое):
1. Нормализация `city_raw -> city_normalized`:
   - убрать префиксы/постфиксы: `м.о.`, `муниципальный округ`, `район`, `р-н`, `ст-ца`, `пос.`, `область` (по правилам, не ломая реальные города),
   - trim, единый регистр, удаление двойных пробелов.
2. Добавить словарь алиасов для частых кейсов.
3. Для нерешенных кейсов сохранить диагностику:
   - `city_raw`,
   - `city_normalized`,
   - причина отказа GIS.

Критерий приемки:
1. Количество `Город не найден в CSV координат` по указанным кейсам уменьшается.
2. В логе есть пара `raw/normalized` для каждого отказа.

## P0.3. Доработка CSV поиска
