# Задание стажеру: исправить Stage 2 и поля в «Все закупки» (без слома фона)

## Контекст
На боевой БД (`c77461_priv_mag_ru`) сейчас:
- в таблице `zakupki` много записей со статусом `raw`;
- в таблице `ai_results` заметно меньше записей;
- в UI `http://priv-mag.ru/stage2` отображается только 1 закупка;
- в UI «Все закупки» у части записей пустые поля `Цена` и `Окончание подачи заявок`.

Текущее поведение Stage 2 завязано на `decisions` (approved stage=1), из-за этого большая часть `raw` закупок в Stage 2 не видна и не идет в ИИ.

## Что нужно сделать

1. Убрать зависимость Stage 2 от таблицы `decisions`.
- Источник данных для Stage 2: таблица `zakupki` со статусом `raw` (и/или `ai_error` для ретрая, если уже есть такой сценарий).
- Не требовать ручного approve на Stage 1 для запуска Stage 2.

2. Исправить API/UI Stage 2 (`/stage2`, `/api/stage2`, связанные репозитории/сервисы).
- Stage 2 должен показывать все закупки, которые реально ожидают ИИ-обработки.
- Количество карточек на Stage 2 должно соответствовать данным в БД (с пагинацией, если уже предусмотрена).

3. Исправить заполнение полей на Stage 1 для «Все закупки».
- При сохранении закупки корректно заполнять:
  - `initial_price` (Цена)
  - `bid_end_date` (Окончание подачи заявок)
- Если поле реально отсутствует в источнике, записывать `NULL`, но не терять значение при наличии в карточке/тексте.

4. Обеспечить совместимость с фоновым режимом (Cron worker).
- Фон (`worker --max-cycles 1`, каждые 5 минут) должен обрабатывать новые `raw` закупки в Stage 2 автоматически.
- Stage 2 в UI и фоновый Stage 2 должны использовать один и тот же критерий выборки.

5. Логирование и диагностика.
- Добавить понятные логи, почему закупка не попала в Stage 2 (если пропущена).
- Логи должны позволять быстро ответить: «сколько `raw` есть», «сколько взяли в Stage 2», «сколько обработано/ошибок».

## Ограничения
- Не ломать текущий flow Stage 1 -> Stage 3.
- Не удалять существующие данные и не делать destructive-миграции.
- Изменения должны работать и на PostgreSQL, и на SQLite (если локально кто-то поднимает SQLite).

## Проверка (обязательно приложить в отчете)

1. SQL-проверки до/после:
- `SELECT COUNT(*) FROM zakupki WHERE status='raw';`
- `SELECT COUNT(*) FROM ai_results;`

2. API-проверки:
- `GET /api/admin/zakupki_all?offset=0&limit=20` — поля `initial_price` и `bid_end_date` отдаются корректно.
- `GET /api/stage2?...` — возвращает закупки из `raw`, а не только из `decisions`.

3. E2E:
- загрузить новые закупки Stage 1;
- запустить Stage 2 (через UI или команду);
- убедиться, что в `ai_results` количество записей увеличилось;
- убедиться, что на странице Stage 2 отображается не 1 карточка, а фактический объем pending-закупок.

## Формат отчета стажера
- Список измененных файлов.
- Что именно изменено по каждому файлу.
- Какие SQL/API/E2E проверки выполнены.
- Скриншоты Stage 1/Stage 2 (до/после).
- Остаточные риски (если есть).
