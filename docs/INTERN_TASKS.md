# Задание стажёру: исправления по ручному прогону + вкладка Stage 4 (админка)

## Контекст
В ручном прогоне обнаружены проблемы:
1. Не отображается `Дата окончания подачи` на:
- вкладке `Загрузка новых` (Stage 1),
- вкладке `Все закупки`,
- вкладке `Этап 3`.
2. При скачивании документов есть ошибка COM Word:
- `Недопустимая строка с указанием класса` в `_extract_doc_via_word(...)`.
3. Нужно добавить отдельную вкладку `Этап 4` в админке.

Работаем только в админской версии.

## Задачи

### 1. Починить поле `bid_end_date` (дата окончания подачи)
Сделать так, чтобы дата стабильно попадала в БД и отображалась во всех нужных таблицах.

Что проверить и исправить:
1. Парсинг Stage 1 (быстрый список ЕИС): корректно извлекается `bid_end_date`.
2. Сохранение выбранных закупок: если `bid_end_date` пустая, подставляется из текста (`combined_text`) fallback-методом.
3. API отдает `bid_end_date` в:
- `/api/stage1`,
- `/api/admin/zakupki_all`,
- `/api/stage3`.
4. Frontend реально рендерит колонку на нужных вкладках.

Критерий:
- После загрузки и сохранения выбранных закупок дата видна на 3 вкладках.

### 2. Обработать ошибку Word COM для `.doc`
Сейчас на части машин нет корректной COM-регистрации Word, и это не должно ломать процесс.

Что сделать:
1. В `text_extraction.py` в `_extract_doc_via_word`:
- при невозможности создать COM-объект не писать пугающую ошибку как критическую;
- корректно переходить на fallback без падения пайплайна.
2. Логгирование:
- один понятный warning/info, что Word COM недоступен;
- без “шумных” повторяющихся трейсбеков на каждый файл.
3. Скачивание/сохранение закупки должно завершаться успешно даже без Word.

Критерий:
- При отсутствии Word COM Stage 1 продолжает обработку документов.
- Закупка сохраняется, UI не ломается.

### 3. Добавить вкладку `Этап 4` в админке
Нужна полноценная админская страница запуска Stage 4.

Минимум:
1. Новая страница `/stage4` и пункт в меню.
2. Таблица закупок, готовых к Stage 4 (например статус `url_ready`), с чекбоксами.
3. Кнопка запуска Stage 4 для выбранных.
4. Пагинация (`Показать еще`) и базовый статус выполнения.
5. Отображение результата:
- сколько закупок обработано,
- сколько объявлений собрано,
- ошибки по конкретным `reg_number` (если есть).

API:
- либо новый `GET /api/stage4` + `POST /api/actions/run_stage4`,
- либо аккуратно переиспользовать существующие endpoint’ы, но без костылей в UI.

Критерий:
- Админ может пройти Stage 4 со страницы `/stage4` без CLI.

## Ограничения
1. Не трогать пользовательский сайт/поток, только админку.
2. Не удалять рабочий функционал Stage 1–3.
3. Не менять схему БД без необходимости.

## Что сдать

3. Короткий отчет:

# Задание стажёру: аудит и стабилизация Этапа 4 (по итогам обсуждений)

## Исходные проблемы (обязательно учесть)

### High
После запуска Этапа 4 закупка исчезает из списка Stage4, хотя UI предполагает просмотр собранных объявлений.

Файлы:
- `src/api/routes.py:420`
- `src/pipeline.py:199`

Причина:
- `/api/stage4` отдаёт только `status='url_ready'`.
- После успешного сбора статус меняется на `listings_fresh`.
- Запись сразу пропадает из левой панели, оператор не может перепроверить результат на той же странице.

### Medium
Автопереоткрытие выбранной закупки после запуска не работает.

Файлы:
- `src/web/static/js/stage4.js:23`
- `src/web/static/js/stage4.js:197`

Причина:
- `loadStage4(true)` сбрасывает `selectedRegNumber = null`.
- Блок `if (selectedRegNumber) { await selectZakupka(selectedRegNumber); }` не выполняется.

### Medium
Нет серверной валидации `top_n`.

Файлы:
- `src/api/routes.py:44`
- `src/api/routes.py:513`

Причина:
- Через API можно передать `0`/отрицательное значение (в обход HTML `min=1`), и это уходит в скрапер.

### Low
Ошибки по закупкам показываются только через `alert + console`.

Файл:
- `src/web/static/js/stage4.js:191`

Причина:
- Нет нормального блока ошибок в интерфейсе (reg_number, причина, действие).

## Новые ключевые требования из последних обсуждений

1. В Этапе 4 должна быть одна каноническая рабочая ссылка: `zakupki.two_gis_url` (из Этапа 3).
2. Этап 4 не должен пересчитывать и не должен перезаписывать ссылку Этапа 3.
3. Если ссылки нет — показывать явное предупреждение: «Ссылки нет (Этап 3)».
4. Убрать путаницу между:
- ссылкой процесса (поиск Этапа 3),
- ссылками карточек объявлений (`/ad/...` и внешние источники).

Важно:
- По проверке БД каноническая ссылка хранится корректно.
- Путаница возникает в UI/парсинге ссылок карточек.

# Задание стажёру: UX-полировка админки (человеческий интерфейс)

## Цель
Сделать админку понятной модератору закупок без технического бэкграунда:
- краткие и ясные названия,
- очевидные действия,
- ссылки на источники рядом с объявлением,
- минимум "догадок", куда нажимать.

## Проблемы, которые нужно исправить

1. Ссылки на источники объявлений (Domclick/Циан/Avito) спрятаны в `Debug` и не видны рядом с карточкой.
2. В интерфейсе смешан язык пользователя и тех.термины (`Top N`, `Debug`, внутренние формулировки).
3. Ключевые кнопки местами расположены нелогично (действие оторвано от списка выбранных элементов).
4. Тексты статусов и кнопок не объясняют следующий шаг оператору.
5. Много `alert/confirm`, мало встроенных сообщений в интерфейсе.

## Обязательные изменения

### 1) Единый понятный язык (русский)
Привести подписи к единому стилю:
- коротко,
- без жаргона,
- без англицизмов в рабочих действиях.

Примеры:
- `Top N` -> `Сколько объявлений`.
- `Debug` -> убрать из основного UI (допустимо оставить в dev-режиме).
- `Запустить Этап 4` -> `Собрать объявления`.

### 2) Ссылки источников рядом с карточкой объявления
На Этапе 4 в каждой карточке объявления отобразить понятный блок ссылок:
- `2ГИС`,
- `Домклик` / `Циан` / `Avito` (если есть).

Правила:
- ссылки должны быть рядом с конкретным объявлением, а не в отдельном техблоке;
- если источника нет, показывать `—`.

### 3) Ясная структура действий
Переразместить элементы так, чтобы путь оператора читался слева-направо:
1. Выбрал закупки.
2. Настроил параметры.
3. Запустил действие.
4. Увидел результат и ошибки.

Особенно проверить:
- Этап 2 (кнопка запуска не должна «висеть» оторвано от контекста).
- Этап 4 (кнопка и статус в одном логическом блоке).

### 4) Человеческие названия статусов
Обновить отображаемые статусы в таблицах админки на понятные формулировки.

Требование:
- по статусу оператор должен понимать, что делать дальше.

### 5) Ошибки и подсказки внутри страницы
Минимизировать `alert/confirm` там, где можно показать:
- inline-ошибку,
- короткую подсказку,
- итог операции в статусном блоке.
