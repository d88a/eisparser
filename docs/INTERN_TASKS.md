## Срочный блок: Stage 2 "висит"/долго стартует (выполняет стажер)

### Контекст
- На проде Stage 2 показывает большую очередь (`pending ~600+`), но фактическая обработка начинается с большой задержкой.
- Пользователь вручную SQL-индексы не создает; это зона ответственности стажера.

### Что сделать (обязательно)
1. Добавить индексы на прод-БД (через Adminer SQL-запросом):
```sql
CREATE INDEX IF NOT EXISTS idx_zakupki_status ON zakupki(status);
CREATE INDEX IF NOT EXISTS idx_ai_results_reg_number ON ai_results(reg_number);
CREATE INDEX IF NOT EXISTS idx_zakupki_processed_at ON zakupki(processed_at);
```

2. Оптимизировать worker Stage 2, чтобы не грузить весь pending дважды:
- В `src/services/worker_service.py` убрать тяжелую предварительную проверку через полный `get_stage2_pending_items()`.
- Проверять наличие задач легким способом: `get_stage2_pending_page(offset=0, limit=1)`.

3. Оптимизировать `run_stage2`:
- В `src/pipeline.py`, когда `reg_numbers` не переданы, брать не полный pending, а страницу сразу по `limit`.
- Не делать полный scan 600+ записей, если цикл обрабатывает только `--limit=10`.

### Проверки
1. До/после по времени старта Stage 2 в логе:
- От строки `Stage 2 started` до первой строки `[1/N] Обработка AI`.

2. Проверка, что очередь обрабатывается:
- есть `Cerebras status: 200`;
- `processed > 0` в итогах Stage 2 (для валидных записей).

3. Проверка, что UI не "зависает" на запуске:
- кнопка запуска отрабатывает;
- есть итоговый статус по обработанным/ошибкам.

### Definition of Done
- Stage 2 начинает обработку без длительной паузы.
- Нет лишних full-scan pending-очереди на каждом цикле.
- Производительность на очереди 600+ записей приемлемая при `limit=10`.
