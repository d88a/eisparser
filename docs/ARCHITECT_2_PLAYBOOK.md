# Руководство для второго архитектора (работа со стажером)

Дата: 2026-03-01  
Контекст: действующий прод на VDS `213.189.219.55`, проект `EIS Parser v2.0`.

## 1. Роль и зона ответственности

Второй архитектор отвечает за:
1. Техническую целостность изменений перед merge/deploy.
2. Постановку задач стажеру с четким `Definition of Done`.
3. Проверку, что изменения не ломают бизнес-контракт Stage 1-4.
4. Подготовку релизов на прод без ручных “точечных” правок на сервере.

Не отвечает за продуктовые решения в одиночку:
1. Изменение статусов и lifecycle без согласования с главным архитектором.
2. Изменение модели монетизации и прав доступа пользователей.

## 2. Текущий целевой продуктовый режим

На ближайший этап:
1. Пользовательская версия работает в бесплатном режиме для всех.
2. Админка остается отдельным контуром (не зависит от пользовательских логинов).
3. Переключатель доступа пользователей: `USER_ACCESS_MODE` (`PUBLIC`/`AUTH_REQUIRED`), по умолчанию `PUBLIC`.

Важно:
1. Любые изменения auth не должны ухудшать доступ админа.
2. Логика пользовательского интерфейса не должна блокировать фоновые Stage 1-4.

## 3. Архитектурные инварианты (ломать нельзя)

### 3.1 Stage-контракт
Источник: `docs/PROJECT.md`, `src/models/statuses.py`.

1. Каноническая ссылка для Stage 4: `zakupki.two_gis_url`.
2. Stage 2 pending только из `raw` и `ai_error`.
3. Stage 4 queue только из `url_ready` и `stage4_error`.

### 3.2 Lifecycle статусов
`raw -> ai_ready | ai_error -> url_ready -> stage4_done | stage4_error`

Все новые статусы и переходы:
1. сначала в `src/models/statuses.py`,
2. потом в pipeline/repository/UI,
3. затем в документацию.

### 3.3 Границы слоев
1. `api/routes/*` не дергают private-методы pipeline/service.
2. Бизнес-логика этапов живет в `pipeline.py` + `services/*`.
3. Репозитории содержат только data-access и SQL.

## 5. Процесс работы “архитектор -> стажер”

## 5.1 Как ставить задачу
Каждая задача стажеру должна содержать:
1. Цель в 1-2 предложениях.
2. Файлы/модули, где разрешено менять код.
3. Явные запреты (что трогать нельзя).
4. Команды проверки и ожидаемый результат.
5. Формат отчета (фактический вывод команд + скрин/лог).

Шаблон DoD:
1. Код компилируется (`python -m compileall -q src`).
2. Проходят релевантные тесты.
3. Нет регрессии по Stage-контракту.
4. Документация обновлена в `docs/*`.

## 5.2 Как принимать задачу
Приемка только после:
1. code review по diff,
2. smoke на API и воркерах,
3. сверки логов с реальным поведением UI.

Если стажер дал “словесный отчет” без команд и вывода:
1. задача не принимается,
2. запросить повторный отчет по формату.

## 6. Checklist code review (обязательно перед deploy)

1. Нет “магических строк” статусов вне `src/models/statuses.py`.
2. Нет прямых private-вызовов между слоями.
3. Нет hardcode секретов/паролей/ключей.
4. Новые endpoint-ы не ломают существующие роуты.
5. Изменения UI Stage 2/4 не нарушают пагинацию и сортировку.
6. Для тяжелых выборок есть pagination + limit.
7. Добавлены/обновлены индексы, если менялась нагрузка на SQL.
8. Документация и runbook обновлены в том же PR/пакете.

## 7. Контур релиза на прод

1. Подготовить список измененных файлов.
2. Сделать backup критичных файлов на сервере (`*.bak_YYYYMMDD`).
3. Загрузить файлы в `/opt/eisparser/src` (без изменений в `.env`).
4. Очистить `__pycache__`.
5. Выполнить `python -m compileall -q /opt/eisparser/src`.
6. Перезапустить сервисы:
   1. `systemctl restart eisparser-api`
   2. `systemctl restart eisparser-worker-ingest`
   3. `systemctl restart eisparser-worker-listing`
7. Выполнить smoke:
   1. `curl -i http://127.0.0.1:8000/`
   2. `curl -i "http://127.0.0.1:8000/api/admin/zakupki_all?offset=0&limit=1"`
   3. Проверить `api.log` и `worker.log`.

Rollback:
1. вернуть `.bak` файлы,
2. перезапустить сервисы,
3. приложить причину отката в отчете.

## 8. Контроль фоновой обработки (операционный минимум)

Каждый день проверять:
1. `systemctl status` всех 3 сервисов.
2. Ошибки в логах за последние 200 строк.
3. Рост счетчиков:
   1. новые закупки в `zakupki`,
   2. свежие `ai_ready`,
   3. свежие `stage4_done`.

Быстрая диагностика “новые закупки не идут”:
1. Проверить доступность ЕИС (нет регламентных работ).
2. Проверить ingest-worker лог на ошибки Stage 1.
3. Проверить `PROXY_URL`, если ЕИС отдает `403/434/5xx`.
4. Проверить, что ingest-worker реально запущен и делает циклы.

## 9. Безопасность (минимальные требования)

1. В проде обязательно отдельный `ADMIN_TOKEN_SECRET` (не равен `ADMIN_PASSWORD`).
2. Для прода рекомендуется `ADMIN_SECURITY_FAIL_FAST=true`.
3. Никогда не публиковать `.env` и ключи в чатах/скринах.
4. После утечки/скрина с секретами: немедленная ротация секретов.

## 10. Документация, которую второй архитектор должен держать актуальной

1. `docs/PROJECT.md` — если менялся контракт этапов/статусов.
2. `docs/DEPLOY_AND_RUN.md` — если менялся процесс деплоя.
3. `docs/WORKER_VDS.md` — если менялся запуск/интервалы воркеров.
4. `docs/VDS_CURRENT_SETUP.md` — если менялись сервисы/пути/окружение.
5. `docs/INTERN_TASKS.md` — только актуальные задачи, без устаревшего шума.

Правило:
1. изменение архитектуры без обновления docs считается незавершенной задачей.

## 11. Приоритеты на ближайший этап (для архитектора + стажера)

1. Стабилизировать публичный пользовательский контур (`USER_ACCESS_MODE=PUBLIC`) без влияния на админку.
2. Убрать “узкие места” на Stage 1 при нестабильности ЕИС (ретраи/прокси/логика деградации).
3. Довести наблюдаемость: понятные метрики и быстрый ответ “почему закупка не прошла этап”.
4. Подготовить основу под коммерциализацию без включения подписки сейчас:
   1. сбор продуктовой аналитики,
   2. учет пользователей/действий,
   3. флаги тарифных ограничений (пока выключены).

## 12. Формат еженедельного отчета второго архитектора

1. Что изменили в архитектуре/коде.
2. Что проверили командами и фактическими результатами.
3. Какие риски остаются.
4. Что передано стажеру на следующую неделю.
5. Что требует решения главного архитектора.
